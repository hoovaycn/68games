## 一句话结论

**音频不是体积大头，图片才是。** 音频 60MB 能压到 13MB（省 46MB），但真正的浪费是 112MB 图片里有 49MB 的 1920×1080 背景图在往一个只有 960×540 的画布里画。

另外，**"换成 OGG 会更小"这个判断不成立** —— 现在项目里的 OGG 反而比 MP3 更大。

## 二、先回答：OGG 格式会更小吗？

**不会。** 文件大小 = 码率 × 时长，跟容器/扩展名没有关系。

看现在的实际数据：

| 格式 | 数量 | 总大小 | 平均码率 |
|---|---|---|---|
| MP3 | 6 首 | 12.17 MB | 160–192 kbps |
| OGG (Vorbis) | 11 首 | 33.44 MB | **300–350 kbps** |
| WAV (PCM) | 1 首 | 13.78 MB | 1411 kbps |

项目里的 OGG 平均比 MP3 **大一倍以上**，因为当初转 OGG 时用了很高的码率。所以：

- 单纯"把 MP3 转成 OGG"→ 体积取决于你设多少码率，跟格式无关
- **正确的问法是"降到多少码率"**，而不是"换成什么格式"

真正有效的两招：**降码率** + **换更高效的编码器**。

## 三、方案 A：BGM 音频（已处理完成，产物可直接用）

### 采用参数

**Opus 64 kbps VBR，48kHz，Ogg 容器**（`-c:a libopus -b:a 64k -application audio`）

为什么是 Opus 而不是 Vorbis：

- Opus 比 Vorbis 效率高约 30%。实测同一首 `bgm_title`：Vorbis q2 转出 1.03MB，Opus 64k 只要 0.84MB
- 本项目是 **Electron（Chromium 内核）+ Windows 桌面版**，Chromium 从 49 版起原生支持 Ogg Opus，**零兼容风险**
- 行业同类做法：Unity / Godot 的 BGM 推荐码率就是 Vorbis 60–100kbps 或 Opus 48–64kbps

### 两个额外发现

**1. `bgm_classroom.mp3` 是伪立体声** —— 左右声道完全一致（差值信号 -91dB，等于静音）。已用单声道 48k 转码，音质比原来每声道 32k 的立体声更好，体积再省 0.35MB。

**2. BGM 目录里有 2 组同名不同格式的文件，代码只会用其中一份：**

| 名称 | 存在版本 | 说明 |
|---|---|---|
| bgm_battle_normal | .ogg (73s/1.59MB) + .mp3 (73s/1.39MB) | 时长、音量几乎一致，疑为同一曲的两个编码 |
| bgm_victory | .ogg (**55s**/2.42MB) + .mp3 (**6.5s**/0.13MB) | **内容完全不同**，短版 6.5 秒 vs 长版 55 秒 |

`src/engine/sound.js` 的 `_loadWithFallback` 回退链是 `.ogg → .mp3 → .wav`，**ogg 存在时 mp3 永远不会被加载**。所以这两个 mp3 在运行时是死文件。

> ⚠️ **关于 `bgm_victory.mp3`（6.5 秒短版）**：该文件**已随本次替换移出**，原文件完整保留在 `audio_optimized/_original_backup/bgm/bgm_victory.mp3`。代码里 `playBgm('bgm_victory')` 因为 ogg 优先，**一直以来播放的都是 55 秒长版**，短版从未被触发，所以本次替换不改变任何运行时行为。若将来需要短版，从备份取回即可。

### 代码改动量：0 处（文件已替换完成）

因为 `sound.js` 已经是 `.ogg` 优先，把产物按同名 `.ogg` 放进 `assets/audio/bgm/`、删掉旧文件即可，**代码一行都不用改，也不会有任何额外 404 请求**（回退链第一顺位就命中）。

> **当前状态：已执行完毕。** `assets/audio/bgm/`、`dist/assets/audio/bgm/` 两个位置均已是 16 个 `.ogg`，旧 mp3/wav 已清除，原始文件全部备份在 `audio_optimized/_original_backup/bgm/`。

### 风险与验证

| 项 | 说明 |
|---|---|
| 兼容性 | Electron/Chromium 原生支持，无需处理 |
| 循环接缝 | Ogg Opus 有 pre-skip 字段，Chromium 会正确跳过。已校验 16 个文件 `start_time=0.000000`。**若实机听出循环处有细微咔哒声**，退到 Vorbis q2（约 96kbps，体积多约 30% 但仍省 70%） |
| 音质 | 64kbps Opus 对游戏 BGM（合成/管弦为主）是标准做法。建议实机戴上耳机过一遍 `bgm_title`、`bgm_intense_boss`、`bgm_home_town` 三首做主观确认 |
| 完整性 | 16 个文件全部通过 ffprobe 校验（codec=opus, 48kHz）与全文件解码测试，无截断 |

### SFX 音效（可选，收益很小）

`assets/audio/sfx/` 17 个 mp3 + 3 个 wav，**总共只有 0.68MB**，压不压对体积没影响。但有一个小问题：

`sfx_fanfare.wav`、`sfx_glass_shatter.wav`、`sfx_suspense.wav` 这三个只有 wav 版本，而代码回退链先试 `.ogg` 再 `.mp3` 才到 `.wav`，**每次播放都会先发两个 404 请求**。建议顺手统一转成 `.ogg`（Opus 96k），既能消掉 404，又能省 0.4MB。优先级低，可以放到最后。

## 四、方案 B：图片（真正的大头，112.4 MB）

### 关键发现：59 张 1920×1080 的背景图在做无用功

`index.html` 里写死了：

```html
<canvas id="game-canvas" width="960" height="540"></canvas>
```

canvas 的绘制缓冲区**固定 960×540**，全屏靠 CSS `transform: scale()` 放大，而且用了 `image-rendering: pixelated`。代码里**没有 devicePixelRatio 处理，也没有任何镜头缩放/推拉逻辑**（已全文检索确认）。

也就是说：一张 1920×1080 的图在 960×540 的 canvas 里绘制时，会被压掉 75% 的像素。放大显示时 canvas 只有 960×540 个像素位，多出来的细节**在屏幕上根本不存在**。

| 分组 | 张数 | 体积 | 平均 | 处理方式 | 预估后 |
|---|---|---|---|---|---|
| backgrounds 1920×1080 | 59 | 49.43 MB | 858 KB | 缩到 960×540 + WebP q82 | ~5.4 MB |
| backgrounds 960×540 | 85 | 21.07 MB | 254 KB | 直接 WebP q82 | ~7.4 MB |
| art 480×640（@2x 立绘） | 174 | 17.11 MB | 101 KB | **WebP 无损** | ~12.8 MB |
| art 240×320（1x 立绘） | 174 | 8.41 MB | 49 KB | **WebP 无损** | ~6.3 MB |
| portraits 192×192 | 127 | 5.00 MB | 40 KB | WebP q85 | ~1.8 MB |
| art 1920×1080（CG） | 8 | 4.70 MB | 602 KB | 缩到 960×540 + WebP | ~0.5 MB |
| backgrounds 480×270 | 26 | 1.64 MB | 65 KB | WebP q85 | ~0.6 MB |
| art 960×540 | 8 | 1.57 MB | 201 KB | WebP q82 | ~0.55 MB |
| portraits 96×96 | 127 | 1.55 MB | 12 KB | WebP q85 | ~0.6 MB |
| 其他（logo/杂项） | ~30 | ~1.0 MB | | WebP | ~0.5 MB |
| **合计** | **1098** | **112.4 MB** | | | **~36 MB** |

> 缩放一项就带来 44MB 收益，而且**视觉上看不出差别**（甚至因为用了比浏览器双线性更好的 Lanczos 重采样，静态截图可能更干净）。

### 实测数据支撑

抽 8 张 1920×1080 背景图（原 7.28MB）实测：

| 处理 | 结果 | 节省 |
|---|---|---|
| PNG 原图 | 7.28 MB | — |
| WebP q82（保持 1920） | 2.22 MB | **70%** |
| 缩 960 + WebP q82 | 0.81 MB | **89%** |

### 立绘必须用**无损** WebP，不能用有损

`art/` 目录的立绘**没有透明通道，而是洋红（#FF00FF）纯色底**，靠 `src/engine/asset_loader.js` 的 `loadWithChromaKey()` 在运行时逐像素抠掉。实测 `zhangzixiao_default@2x.png` 洋红像素占 46.8%，alpha 全不透明。

有损压缩（WebP lossy / AVIF / JPEG）会在角色边缘产生色度渗色，抠图后会**留下明显的粉色描边**。

已验证：**WebP 无损转码后转回 PNG，307200 个像素差异 0 个（0.000%）**，洋红底完全保真，抠图逻辑零影响。代价是立绘只能省 25%，不是 70%。

> 若想进一步压立绘（可省到 70%），需要改成"预抠图 + 带 alpha 的 WebP" —— 这会让 `chromaKey` 变成空操作，属于代码改动，且需要目检边缘质量。**建议先不做。**

### 需要研发确认的两个点

1. **`portraits/` 192×192 是否带透明通道？** 有的话走 WebP 有损 + alpha 时可以，但边缘需目检；保险做法是同立绘一样用无损。
2. **同一张图 1x / 2x 成对存在（art 174 对、portraits 127 对）**，两份都在用（首屏 `main.js:513` 预加载列表里明确用了 1x 版），**不能删任何一份**。

**批量替换规则**：把所有字符串字面量里的 `.png'` / `.png"` 改为 `.webp'` / `.webp"`。注意不要误改注释里的文字。

**两个容易漏的地方：**

1. `src/engine/avatar.js:702` —— `artForEmotion()` 里是**拼接**出来的路径：
   ```js
   return 'assets/art/' + base + densitySuffix(density) + '.png';
   ```
   这行是硬编码 `.png` 后缀，批量替换能命中，但改完要单独回查这个函数。

2. `src/ui/finale_screen.js:21-22` —— 有 `bgImgSrc` 和 `bgImgFallback` 两个字段，**两个都要改**，否则 fallback 会去找不存在的 png。

**建议保留的兼容处理**：如果担心遗漏，可以在 `AssetLoader` 的加载失败回调里加一次性 `.png` 回退（一行为一个 if）。但更推荐一次性做干净，不引入隐式回退。

### 5.3 构建脚本的坑（必须处理）

`tools/copy_assets_to_dist.cjs` 用的是：

```js
fs.cpSync(src, dest, { recursive: true, force: true });
```

**它只覆盖、不删除**。这意味着：你在 `assets/` 里删掉的旧 `.png` / `.mp3`，**会一直留在 `dist/assets/` 里**，打出来的包体型一点没变小（可能还会新旧并存）。

所以每次转换后必须手动清理：

```bash
rm -rf dist/assets/art dist/assets/backgrounds dist/assets/portraits
rm -rf dist/assets/audio
# 然后重新 npm run build
```

或者改 `copy_assets_to_dist.cjs`，在复制前先清空目标子目录。这是研发的事，我只提示这个坑。
